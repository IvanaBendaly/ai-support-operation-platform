# C04 — Policy knowledge retrieval

## Architecture and service contract

`RetrievalService(sessions, RetrievalSettings()).search(question)` returns typed
`RetrievalResult` evidence, independently of support-case state, business actions,
or model decisions. All Must Build and Strong Additions are implemented. There is
no external embedding provider, distributed search service, personalization or
multilingual indexing in this feature.

The local representation is corpus-trained latent semantic analysis (LSA):
normalized TF-IDF rows are projected through a truncated singular value
decomposition. NumPy is the only new runtime dependency; its version is locked.
This is an inspectable, bounded alternative to remotely generated embeddings,
not a claim of pretrained language-model quality. It works best on a small English
support corpus and needs evaluation before use on a substantially different corpus.
The implementation uses [NumPy's reduced SVD](https://numpy.org/doc/stable/reference/generated/numpy.linalg.svd.html).

The ranking pipeline is:

1. Normalize English terms, selected inflections and support synonyms. Apply small,
   explicit phrase reformulations such as “money back” → “refund” and “locked out”
   → “login password”. No policy facts are generated by reformulation.
2. Compare the query with persisted latent section vectors using cosine similarity.
   Combine semantic score (45%) with normalized TF-IDF keyword score (55%).
3. Take a bounded candidate set. Rerank using 80% hybrid score and 20% matched-query
   concept coverage. Reject candidates with no lexical/concept overlap; broad latent
   association alone is insufficient evidence. Apply the minimum score threshold.
4. Return whole sections within result, per-section and context limits. Citation
   headers count toward the context budget. Sections are never silently cut in a
   way that could drop a qualification or negation.

Tie breaking uses policy identifier, document version and section ordinal. Training
uses sorted vocabulary and fixed SVD signs, with no random seed or network call.
Ranking scores are rounded to six decimals. Rebuilds in the locked runtime reproduce
results; exact floating-point bytes across different BLAS implementations are not
promised. Index generation UUIDs and durations are intentionally not deterministic.

The returned result includes the original query, effective UTC time, settings,
query expansions, model identifier, index generation/status/size, duration,
result count, bounded model context and evidence. Every evidence entry includes
section/document/policy IDs, document version, filename, original page/section
reference, ordinal, full readable section text, semantic/keyword/final scores and
query coverage. Scores are ranking signals, **not probabilities of correctness**.
Only `context` is intended for bounded model input; do not concatenate it with the
same texts in `evidence`, which are structured citation metadata for callers.

| Result status | Meaning |
| --- | --- |
| `matched` | Relevant candidates passed the configured checks |
| `ambiguous` | Different policies have similarly scored leading candidates |
| `insufficient_evidence` | Low query coverage or context limits prevent complete candidate delivery |
| `no_matches` | No active documents or no relevant candidate sections |

These statuses do not decide policy applicability, resolve policy conflicts or
authorize actions. Downstream C07/C09 must inspect the cited evidence and customer
circumstances. General or unsupported questions may require clarification.

## Atomic index and lifecycle consistency

Migration `0005` adds `knowledge_retrieval_index`. A singleton row stores the entire
bounded snapshot: model ID, generation, source fingerprint, payload checksum,
vocabulary, IDF weights, projection matrix, source section IDs and section vectors.
The complete snapshot commits atomically. There is no separately committed vector
batch that could become a partial “successful” index.

Every search synchronizes against C03's authoritative active-document query. It
includes effective times, expiry, failed replacements, deactivation and permanent
supersession. If sources or model settings change, a new snapshot replaces the old
one, removing obsolete vectors. Until the next search/rebuild, old bytes can remain
stored, but they cannot be searched through the service without synchronization.
Call `synchronize(force=True)` for explicit preparation or repair. No scheduler is
required for scheduled activation: the next search observes the effective time.

The index row is locked during synchronization/search. Concurrent first creation
can yield a retryable storage conflict; subsequent searches serialize on the row.
After ranking, the service rechecks source eligibility before returning evidence.
A lifecycle change observed during search yields `index_changed`, not stale evidence.
Results are snapshots as of `effective_at`, not leases on future policy validity;
a later workflow should retrieve again before relying on older saved evidence.

Payload checksums, section coverage, array dimensions and finite values are
validated. A corrupt/incomplete unchanged index fails closed until an explicit
rebuild. A failed rebuild rolls back to the prior stored generation; an outdated
generation is never used as a fallback for the current corpus.

`RetrievalFailure` (a `DomainError`, HTTP 503 in the admin API) distinguishes
`index_unavailable`, `index_corrupt`, `source_inconsistent`, `index_changed`,
`representation_unavailable`, and `corpus_limit` from valid empty evidence.
Computation failures and unavailable storage expose safe messages without underlying
SQL, credentials or query contents. The local representation provider needs no API
key; injected computation failures exercise the equivalent provider-failure boundary.

## Configuration and bounded operation

`Settings.retrieval` is a validated, immutable `RetrievalSettings`. Locally, use
`NORTHSTAR_RETRIEVAL__CONTEXT_CHARS=8000` or the corresponding JSON setting
`NORTHSTAR_RETRIEVAL={"context_chars":8000}`. Compose forwards the three common
result/context/section limit variables; other overrides can be added to the backend
environment when required. The admin search API cannot override server limits.

| Setting | Default | Meaning |
| --- | ---: | --- |
| `result_limit` | 5 | Maximum returned evidence sections |
| `context_chars` | 8000 | Complete model-context character budget, including citations |
| `section_chars` | 2000 | Maximum complete section length; longer sections are omitted with a budget warning |
| `query_chars` | 2000 | Maximum query length |
| `candidate_limit` | 20 | Maximum reranked candidates; at least result_limit |
| `min_score` | 0.22 | Minimum final ranking score |
| `ambiguity_margin` | 0.06 | Leading cross-policy score difference considered ambiguous |
| `dimensions` | 32 | Maximum latent dimensions, bounded by corpus rank |
| `max_sections` | 256 | Active corpus limit; exceeding it is a failure, not silent truncation |
| `max_vocabulary` | 4096 | Most frequent terms retained, with deterministic ties |

Full in-process indexing/search is appropriate for this portfolio corpus. Bounds
cap matrix size; increasing the corpus limit is not a substitute for designing a
larger search system. Corpus changes rebuild the snapshot, so this design favors
small policy collections with relatively infrequent updates.

## API and portfolio demonstration

Run the documented migrations and set the existing private `NORTHSTAR_ADMIN_TOKEN`.
Both endpoints require the same administrator bearer authentication as C03:

- `POST /api/admin/retrieval/index` explicitly rebuilds the current active corpus.
- `POST /api/admin/retrieval/search` accepts JSON `{"query":"I want my money back"}`.

Swagger at `/docs` documents the request and structured response. The reusable
internal service does not make HTTP calls or require an administrator token; its
caller is responsible for authorization. No public customer search API is added.

From the repository root:

```powershell
.\.venv\Scripts\python.exe scripts/retrieval_demo.py
```

The demo uses a disposable SQLite **test** database and the same fixed corpus as
`backend/tests/test_retrieval.py`. It prints actual results with citations, an
unrelated-query empty response, a replacement with version history and old-version
exclusion, and deactivation. It does not change the configured business database.

The executed fixed-corpus tests cover these expected top selections:

| Question | Top policy |
| --- | --- |
| Can I get a refund for my paid invoice? | refunds |
| I want my money back | refunds |
| How can I cancel my subscription? | cancellation |
| I want to stop paying | cancellation |
| How do I reset my password? / I am locked out | login |
| Where can I check a service outage? | outage |
| Can I upgrade my plan to Growth? | upgrade |
| Where are invoice receipts? | invoices |
| How do I export customer data? | export |
| How can I delete personal data? | deletion |
| astronomy telescope galaxies | explicit no matches |

These are functional fixtures, not a broad retrieval-quality benchmark. The suite
also verifies actual PDF page citations, deterministic persisted/rebuilt results,
ambiguous evidence, source lifecycle changes during search, context caps, corrupt
vectors, atomic rollback, safe failure responses, API authorization and index model
changes. Primary PostgreSQL lifecycle/concurrency tests require an empty disposable
`NORTHSTAR_TEST_DATABASE_URL`; skipped tests are not claimed as verified.

A captured run is available in [the demo output](../examples/retrieval-demo.json).
Its document IDs identify records in that disposable run, not the live database.
